# Gate reference — the registry, in full

**A gate is an ID in `contracts/gates.yml`, never a path on disk** (decision D-3). This page is the
readable form of that file, and it is **generated** — every count below is computed from the
registry at build time, so it cannot go stale the way a hand-typed number does.

> **Do not edit this file.** Run `python scripts/build_docs_reference.py` to regenerate it; the prose
> lives in that script. `GATE-DOCS-CURRENT` fails on a hand-edit.

Regenerate your own view of any of it at any time:

```bash
architect-cli gate list                      # the whole registry
architect-cli gate list --kind native        # the in-process gates
architect-cli gate run --id GATE-SDD-CHECK ./spec # current deterministic check
architect-cli gate explain <FINDING-CODE>    # every emitter, and the argv to reproduce
architect-cli gate bootstrap --check         # exit 0 = the file matches the scripts on disk
```

## 6 · Reading a gate result

```
ran 20 · passed 10 · failed 10
```

Each failure is named with **its own exit code**. `GateResult` keeps `exit_code` alongside
`findings` rather than collapsing to a boolean, because a gate that crashed and a gate that found
nothing must never read the same.

| Exit | Means |
|---|---|
| `0` | pass only when the selected gate ran and passed |
| `1` | blocking findings |
| `2` | invocation or required-input error |
| `3` | incomplete evidence or unsupported current workspace |

A skipped result is NOT_APPLICABLE. It is not PASS. An all-skipped set does not authorize release.

**A fully green first pass is a defect report, not a milestone** (rule R-4). The audited runs that
motivated this registry scored 121 and 52 self-graded `PASS` rows respectively.

## 7 · How the derivation of finding codes was widened, and why not further

Two codes were emitted by their gate's source but absent from that entry's derived `findings`, so
`architect-cli gate explain` reported an unknown code for both:

| Code | Emitted at | Why the derivation missed it |
|---|---|---|
| `ORPHAN` | `scripts/check_doc_coverage.py` | **no hyphen** — the shape pattern requires one |
| `ROW-VERIFY-NOT-A-GATE` | `scripts/check_checklist.py` | a **one-character segment** (`-A-`) — the pattern required two |

Both are load-bearing: `ORPHAN 0` is the condition the site build waits on, and
`ROW-VERIFY-NOT-A-GATE` is the `--strict-honesty` half of checklist verification.

**Fixed by reading the emitter position, not by loosening the shape.** A second pattern matches
whatever sits in the first argument of an emitter call — `add(...)`, `self.add(...)`,
`Finding(...)` — because a string only becomes a finding code by being *reported* as one.

That distinction cuts both ways, and this generator was the first to prove it. Its code annotations
started life as Python literals, so the derivation registered **this script** as emitting all 44
codes it merely names. A script that prints a code is not a gate that raises one. The annotations
moved to `scripts/docs_reference_codes.yml`, and the prose above stopped quoting emitter-call syntax
verbatim, because the derivation is right to read that syntax as an emitter wherever it appears.

Loosening the shape pattern was tried first and rejected on evidence: it adds 59 entries, of which
`A-Z`, `A-Z0-9`, `A-F0-9` and `UTF-8` fall out of regex character classes and `DC-1`, `BP-5`,
`W-12`, `MOD-4` are rule ids cited in comments. A derivation that reports a character class as a
finding code is worse than one that misses a code.

Locked in by `tests/test_gate_registry.py::test_single_word_and_single_letter_codes_are_derived` and
its negative control `test_no_regex_character_class_is_derived_as_a_finding_code`.
